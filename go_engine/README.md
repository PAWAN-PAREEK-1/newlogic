# Go Simulation Engine for the Stake Engine Math SDK

A drop-in replacement for the Python SDK's *simulation* stage
(`create_books`), written in Go. It produces **byte-identical output** to the
Python engine — same books, same lookup tables, same force files — but runs
the hot loop in native code across all CPU cores in a single process.

```
Python engine, 3,800 sims, 1 process ......... ~4.5 s
Go engine,     3,800 sims, 12 workers ........ ~0.12 s
Go engine,   600,000 sims, 12 workers ........ ~45 s   (all 6 modes)
```

Only simulation moved to Go. Everything else is unchanged SDK:

```
game_config.py ──export_spec.py──> game_spec_go.json
                                        │
                                   go_engine (this)          <- SIMULATE
                                        │ books / LUTs / forces
generate_configs (Python)               │                    <- CONFIGS
optimization_program (Rust)             │                    <- OPTIMIZE
game_analytics + rgs_verification (Python)                   <- ANALYZE/VERIFY
```

Run the whole pipeline with:

```bash
python games/expwilds/run_go.py
```

## Why the output is byte-identical (and why that matters)

The Python engine seeds `random.seed(sim + 1)` per simulation, making every
book a pure function of its simulation number. This engine re-implements
CPython's exact random machinery in [`pyrand/`](pyrand/pyrand.go):

* MT19937 with CPython's `init_by_array` integer seeding,
* `random()` as `genrand_res53`,
* `getrandbits`-based rejection sampling for `randrange` / `choice`,
* `random.choices` cumulative-weight bisection,
* `random.shuffle`'s Fisher–Yates,

plus CPython's decimal-string rounding (`round(x, 2)`) and `repr()` float
formatting ([`engine/pyfmt.go`](engine/pyfmt.go)), and `json.dumps` output
formatting ([`engine/pyjson.go`](engine/pyjson.go)).

Because both engines produce identical bytes for identical inputs:

1. **The port is testable** — any logic bug shows up as a file diff against
   the Python engine (this was validated on all bet modes).
2. **Every book is reproducible** from `(game spec, mode, sim number)` in
   either language — a useful property for audits.
3. **You can switch engines at any time** without invalidating published
   math or re-verifying the frontend.

`pyrand` is proven against reference vectors generated by CPython
(`go test ./pyrand/`). If those tests fail, fix that before anything else.

| `engine/events.go` | `events.py` | book event emitters |
| `engine/book.go` | `books.py` | book → JSON |
| `engine/winmanager.go` | `win_manager.py` | win accounting |

| `engine/force.go` | `write_data.py` (forces) | force-record aggregation |

| `game/expwilds.go` | `games/expwilds/*.py` | THE GAME (spin/feature logic) |
| `main.go` | `run.py` (sim part) | CLI |

## Running it directly

`run_go.py` does all of this for you; the raw CLI is:

```bash
cd go_engine
go build -o bin/engine .
./bin/engine \
  --spec    ../games/expwilds/library/configs/game_spec_go.json \
  --library ../games/expwilds/library \
  --modes   base,ante,bonus \
  --sims    100000              # or per-mode: base=200000,bonus=50000
  --workers 0                   # 0 = all cores
  --batch   10000               # sims buffered per batch
```

## Determinism rules (read before touching engine/game code)

The Python and Go engines only stay in lockstep if **every RNG draw happens
in the same order**. Things that look like waste are load-bearing:

* `CreateSymbol("W")` during free games draws a multiplier via the special-
  symbol hook even when the caller immediately overwrites it — Python does
  the same, so the draw must stay.
* Retried rounds (criteria not met) continue the same RNG stream; the seed is
  per-simulation, not per-attempt.
* Weighted tables iterate in the order declared in `game_config.py` — that is
  why the spec exports them as arrays, and why `engine.Conditions` stores
  slices, never maps.
* Worker count does NOT affect output: simulations are independent streams,
  and the runner writes results in simulation order.

If you intentionally change game logic, change it in **both** engines (or
accept divergence and stop claiming byte-parity — remove the comparison test
from your workflow in that case).

## Porting another game to the Go engine

1. **Export**: copy `games/<game>/export_spec.py` and extend
   `_export_conditions` with any new condition tables your game uses.
2. **Game logic**: copy `game/expwilds.go` as a starting point. Re-implement
   your `gamestate.py` flow using the engine primitives
   (`DrawBoard`, `GetLines`, events, `RunFreespinFromBase`, …). Follow the
   original Python file top-to-bottom and keep RNG calls in order.
3. **Hooks**: register special-symbol functions and overrides in `Attach()`
   (the Go equivalent of the `GameStateOverride` subclass chain).
4. **New mechanics** (tumbles, ways pays, clusters): port the corresponding
   `src/calculations/*.py` file into `engine/` next to `lines.go`.
5. **Validate**: run both engines at a few thousand sims and diff the
   outputs. Byte-equality = your port is correct. This is the only test that
   matters.

## Verification harness

To re-run the parity check at any time (both engines, small counts, full
byte-diff of every output file):

```bash
python go_engine/tools/verify_parity.py
```

Run it after any change to game logic in either engine. `ALL PASS` means the
Go port is still a faithful mirror of the Python reference.

## Requirements

* Go ≥ 1.22 (uses `github.com/klauspost/compress` for zstd books)
* The Python SDK venv for the rest of the pipeline (export, optimize, verify)
